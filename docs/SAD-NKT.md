# PHẦN 1: TỪ MONOLITHIC ĐẾN MICROSERVICES VÀ DDD

Phần này trình bày hành trình tiến hóa của kiến trúc phần mềm, từ mô hình nguyên khối truyền thống (Monolithic) sang kiến trúc vi dịch vụ (Microservices) hiện đại, kết hợp với phương pháp thiết kế hướng miền (Domain Driven Design – DDD). Đây là nền tảng lý thuyết cốt lõi để hiểu cách các hệ thống phần mềm quy mô lớn được xây dựng và vận hành trong thực tế ngày nay.

## 1.1 Giới Thiệu Monolithic Architecture

### 1.1.1 Khái Niệm

Monolithic Architecture (Kiến trúc nguyên khối) là mô hình thiết kế phần mềm trong đó toàn bộ ứng dụng được xây dựng, triển khai và vận hành như một đơn vị phần mềm duy nhất, thống nhất. Tất cả các thành phần chức năng — giao diện người dùng (UI), logic nghiệp vụ (business logic), lớp truy cập dữ liệu (data access layer) — đều nằm trong cùng một codebase và được biên dịch, đóng gói thành một artifact duy nhất (ví dụ: file .war, .jar, .exe).

| **Định nghĩa cốt lõi** |
| --- |
| Monolithic = "Một khối duy nhất" — toàn bộ ứng dụng là một process đơn lẻ |
| Tất cả module giao tiếp qua lời gọi hàm (in-process calls) thay vì network calls |
| Triển khai theo kiểu all-or-nothing: thay đổi nhỏ cũng cần deploy lại toàn bộ ứng dụng |
| Cơ sở dữ liệu thường là một database tập trung, dùng chung cho toàn ứng dụng |

### 1.1.2 Cấu Trúc Điển Hình

Một ứng dụng Monolithic điển hình thường được tổ chức theo mô hình phân tầng (layered architecture) gồm 3–4 tầng chính:

| **Tầng** | **Tên thành phần** | **Chức năng** |
| --- | --- | --- |
| **Tầng 1** | Presentation Layer | Xử lý giao diện người dùng, nhận HTTP request, trả về HTML/JSON |
| **Tầng 2** | Business Logic Layer | Xử lý quy tắc nghiệp vụ, tính toán, kiểm tra điều kiện |
| **Tầng 3** | Data Access Layer | Kết nối và thao tác với cơ sở dữ liệu (CRUD) |
| **Tầng 4** | Database Layer | Lưu trữ dữ liệu (PostgreSQL, MySQL, Oracle...) |

Mọi module (User Management, Order Processing, Payment, Inventory...) đều nằm trong cùng một project, gọi hàm của nhau trực tiếp. Điều này giúp chia sẻ code dễ dàng nhưng cũng tạo ra sự phụ thuộc chặt chẽ (tight coupling) giữa các module.

### 1.1.3 Ví Dụ Thực Tế

Hệ thống thương mại điện tử xây dựng theo kiến trúc Monolithic điển hình:

```
ecommerce-app/├── src/│   ├── controllers/          # Presentation Layer│   │   ├── UserController.java│   │   ├── OrderController.java│   │   ├── ProductController.java│   │   └── PaymentController.java│   ├── services/             # Business Logic Layer│   │   ├── UserService.java│   │   ├── OrderService.java│   │   ├── InventoryService.java│   │   └── PaymentService.java│   ├── repositories/         # Data Access Layer│   │   ├── UserRepository.java│   │   └── OrderRepository.java│   └── models/               # Domain Models│       ├── User.java│       ├── Order.java│       └── Product.java└── pom.xml                   # Build artifact → ecommerce-app.war
```

Các hệ thống monolith nổi tiếng trong lịch sử: Amazon.com (trước 2004), eBay (trước 2002), Netflix (trước 2009), Uber (trước 2014). Tất cả đều bắt đầu bằng monolith và sau đó chuyển sang microservices khi quy mô tăng lên.

### 1.1.4 Nhược Điểm Chi Tiết

Mặc dù đơn giản trong giai đoạn đầu, Monolithic Architecture bộc lộ nhiều hạn chế nghiêm trọng khi hệ thống phát triển:

| **Nhược điểm 1: Khó Scale (Scalability Problem)** |
| --- |
| Buộc phải scale toàn bộ ứng dụng dù chỉ một module bị quá tải |
| Ví dụ: Module thanh toán có lưu lượng cao vào Black Friday → phải scale cả hệ thống, lãng phí tài nguyên |
| Không thể scale độc lập từng phần chức năng theo nhu cầu thực tế |

| **Nhược điểm 2: Khó Triển Khai (Deployment Problem)** |
| --- |
| Thay đổi nhỏ (sửa 1 dòng code) cũng yêu cầu build và deploy lại toàn bộ ứng dụng |
| Thời gian downtime cao, rủi ro regression lớn khi release |
| Khó áp dụng CI/CD pipeline hiệu quả với chu kỳ release nhanh |

| **Nhược điểm 3: Tight Coupling & Technical Debt** |
| --- |
| Các module phụ thuộc chằng chịt nhau, khó tách biệt và test độc lập |
| Codebase phình to theo thời gian, khó hiểu, khó maintain |
| Hiện tượng "Big Ball of Mud" — không ai hiểu toàn bộ hệ thống |
| Refactor cực kỳ rủi ro vì thay đổi một nơi có thể phá vỡ nhiều nơi khác |

| **Nhược điểm 4: Technology Lock-in** |
| --- |
| Toàn bộ ứng dụng buộc phải dùng cùng một ngôn ngữ lập trình, framework, phiên bản |
| Không thể áp dụng công nghệ phù hợp nhất cho từng bài toán cụ thể |
| Nâng cấp version của một thư viện có thể gây conflict với toàn bộ hệ thống |

| **Nhược điểm 5: Fault Isolation (Độ bền kém)** |
| --- |
| Một module bị lỗi (memory leak, infinite loop) có thể làm sập toàn bộ ứng dụng |
| Không có cơ chế cô lập lỗi tự nhiên giữa các thành phần |
| Single point of failure: một process duy nhất chứa tất cả |

### 1.1.5 Khi Nào Nên Dùng Monolithic

Dù có nhiều nhược điểm ở quy mô lớn, Monolithic Architecture vẫn là lựa chọn hợp lý trong nhiều trường hợp:

| **Nên dùng Monolithic khi:** |
| --- |
| Startup / MVP giai đoạn đầu: cần ra thị trường nhanh, team nhỏ (< 10 người), yêu cầu nghiệp vụ chưa ổn định |
| Hệ thống nội bộ nhỏ: ít người dùng, không yêu cầu high availability, ít thay đổi |
| Domain chưa được hiểu rõ: khi chưa xác định được ranh giới các subdomain, monolith dễ refactor hơn |
| Team thiếu kinh nghiệm distributed systems: Microservices đòi hỏi kỹ năng cao về DevOps, networking, observability |
| "Monolith First" pattern (Martin Fowler): bắt đầu bằng monolith, khi hiểu rõ domain mới tách ra microservices |

## 1.2 Microservices Architecture

### 1.2.1 Khái Niệm

Microservices Architecture là một phương pháp thiết kế phần mềm trong đó ứng dụng được cấu thành từ một tập hợp các dịch vụ nhỏ, độc lập (services), mỗi service:

**Chạy trong process riêng biệt **

và giao tiếp với nhau qua các cơ chế nhẹ (thường là HTTP/REST API hoặc message queue)

**Được xây dựng xung quanh một business capability **

cụ thể, tương ứng với một subdomain trong hệ thống

**Có thể deploy độc lập **

mà không ảnh hưởng đến các service khác

**Có thể sử dụng công nghệ khác nhau **

(polyglot programming và persistence)

**Có database riêng **

— đây là nguyên tắc quan trọng nhất để đảm bảo tính độc lập

Thuật ngữ "Microservices" được James Lewis và Martin Fowler phổ biến vào năm 2014. Khái niệm này nhanh chóng được các công ty công nghệ lớn như Netflix, Amazon, Uber, Spotify áp dụng thành công, trở thành tiêu chuẩn cho hệ thống quy mô lớn.

### 1.2.2 Đặc Điểm

Microservices có các đặc điểm nhận dạng sau:

**Single Responsibility: **

Mỗi service chỉ làm tốt một việc duy nhất, tập trung vào một business capability

**Loosely Coupled: **

Services ít phụ thuộc vào nhau nhất có thể. Thay đổi nội bộ một service không ảnh hưởng đến service khác

**Highly Cohesive: **

Tất cả code liên quan đến một business capability được gom vào cùng service

**Decentralized Data Management: **

Mỗi service sở hữu database riêng, không share database với service khác

**Failure Isolation: **

Lỗi ở một service không lan truyền sang service khác (circuit breaker pattern)

**Technology Diversity: **

Mỗi service có thể được viết bằng ngôn ngữ phù hợp nhất (Java, Python, Go, Node.js...)

**Automated Deployment: **

CI/CD pipeline độc lập cho từng service

### 1.2.3 So Sánh Monolithic vs Microservices

| **Tiêu chí** | **Monolithic** | **Microservices** |
| --- | --- | --- |
| **Codebase** | Một codebase duy nhất | Nhiều codebase độc lập, mỗi service một repo |
| **Triển khai** | Deploy toàn bộ ứng dụng cùng lúc | Deploy từng service độc lập |
| **Scalability** | Scale toàn bộ ứng dụng | Scale từng service theo nhu cầu |
| **Database** | Một database tập trung, dùng chung | Mỗi service có database riêng |
| **Giao tiếp** | In-process calls (gọi hàm trực tiếp) | IPC: HTTP/REST, gRPC, Message Queue |
| **Công nghệ** | Cùng ngôn ngữ, framework, version | Polyglot: mỗi service dùng tech phù hợp |
| **Fault Isolation** | Lỗi lan truyền trong toàn ứng dụng | Lỗi cô lập trong từng service |
| **Độ phức tạp vận hành** | Đơn giản (một process) | Phức tạp cao: nhiều service, network, logging... |
| **Phù hợp với** | Team nhỏ, hệ thống đơn giản, MVP | Team lớn, hệ thống phức tạp, high-scale |
| **Thời gian phát triển ban đầu** | Nhanh hơn | Chậm hơn (cần infrastructure phức tạp hơn) |

1.2.4 Ưu Điểm

| **Ưu điểm của Microservices Architecture** |
| --- |
| Independent Deployability: Deploy một service mà không cần deploy lại toàn hệ thống → giảm risk, tăng tốc độ release |
| Granular Scalability: Scale riêng Payment Service khi cần, không cần scale cả hệ thống → tiết kiệm tài nguyên |
| Technology Flexibility: Team Payment dùng Java, team Recommendation dùng Python ML, team API Gateway dùng Node.js |
| Fault Tolerance: User Service bị crash không ảnh hưởng đến Order Service, Product Service vẫn hoạt động |
| Team Autonomy: Mỗi team sở hữu hoàn toàn một service, làm việc độc lập, không chặn lẫn nhau |
| Easier Refactoring: Rewrite một service nhỏ dễ hơn nhiều so với refactor monolith lớn |
| Better Observability: Monitor, trace, log từng service độc lập, dễ debug hơn |

### 1.2.5 Nhược Điểm

| **Nhược điểm và thách thức của Microservices** |
| --- |
| Distributed Systems Complexity: Network calls có độ trễ, có thể fail → cần xử lý timeout, retry, circuit breaker |
| Data Consistency: Không có distributed transaction như RDBMS, phải dùng Saga Pattern, Eventual Consistency |
| Service Discovery: Làm thế nào để các service tìm thấy nhau? Cần service registry (Consul, Kubernetes DNS) |
| Operational Overhead: Cần Kubernetes, Docker, API Gateway, Service Mesh, distributed tracing (Jaeger), ELK Stack... |
| Testing Complexity: Integration test và end-to-end test phức tạp hơn nhiều khi có nhiều service |
| Network Security: Giao tiếp giữa services qua mạng → cần mTLS, authentication, authorization giữa services |
| Latency: Chain of service calls (A → B → C → D) tích lũy độ trễ, có thể ảnh hưởng đến trải nghiệm người dùng |

### 1.2.6 Nguyên Tắc Thiết Kế

Để thiết kế Microservices hiệu quả, cần tuân thủ các nguyên tắc sau:

| **Nguyên tắc** | **Mô tả và cách áp dụng** |
| --- | --- |
| Single Responsibility | Mỗi service chỉ phụ trách một business capability. Nếu mô tả service cần dùng từ 'và', đó là dấu hiệu service đang làm quá nhiều việc |
| Database per Service | Mỗi service có database riêng, không truy cập trực tiếp vào database của service khác. Giao tiếp qua API hoặc events |
| API First Design | Thiết kế API (contract) trước khi implement. Dùng OpenAPI/Swagger để document và share contract giữa các team |
| Fail Fast & Circuit Breaker | Service phải fail nhanh khi dependency không khả dụng. Circuit breaker ngăn cascade failures |
| Design for Failure | Giả định mọi service đều có thể fail bất cứ lúc nào. Implement retry, timeout, fallback cho mọi service call |
| Idempotency | Các API phải đảm bảo gọi nhiều lần cho cùng kết quả. Quan trọng khi retry sau lỗi mạng |
| Event-Driven Communication | Dùng message queue (Kafka, RabbitMQ) cho giao tiếp async giữa services để giảm coupling |

### 1.2.7 Thiết kế hệ thống Microservices khác Monolithic như thế nào?

Mặc dù Monolithic và Microservices đều có mục tiêu xây dựng một hệ thống phần mềm hoàn chỉnh, cách thiết kế của hai kiến trúc này khác nhau rất rõ. Monolithic thường thiết kế hệ thống như một khối thống nhất, các module nằm chung trong một codebase, dùng chung database và được triển khai cùng nhau. Ngược lại, Microservices chia hệ thống thành nhiều service nhỏ, mỗi service phụ trách một năng lực nghiệp vụ riêng, có thể phát triển, triển khai và mở rộng độc lập. Theo James Lewis và Martin Fowler, microservices là cách xây dựng ứng dụng như một tập hợp các service nhỏ, chạy trong process riêng và giao tiếp bằng cơ chế nhẹ như HTTP API.

| **Khía cạnh thiết kế** | **Monolithic Architecture** | **Microservices Architecture** |
| --- | --- | --- |
| Cách chia hệ thống | Chia theo layer kỹ thuật như Controller, Service, Repository, Database | Chia theo business capability như User Service, Order Service, Payment Service |
| Ranh giới module/service | Ranh giới chủ yếu nằm trong code, dễ bị phụ thuộc chéo | Ranh giới nằm ở service/API, rõ ownership và trách nhiệm |
| Database | Thường dùng một database chung cho toàn hệ thống | Mỗi service nên sở hữu database riêng, không truy cập trực tiếp database của service khác |
| Giao tiếp nội bộ | Gọi hàm trực tiếp trong cùng process, tốc độ nhanh | Gọi qua network bằng REST, gRPC hoặc message queue |
| Transaction | Dễ dùng transaction ACID trong cùng database | Khó dùng transaction toàn cục, thường dùng Saga Pattern hoặc Eventual Consistency |
| Deploy | Deploy toàn bộ ứng dụng cùng lúc | Deploy từng service độc lập |
| Scale | Scale cả ứng dụng, kể cả phần không cần nhiều tài nguyên | Scale riêng service có tải cao, ví dụ Payment hoặc Recommendation |
| Xử lý lỗi | Lỗi ở một module có thể làm ảnh hưởng toàn bộ ứng dụng | Lỗi được cô lập theo service, cần timeout, retry, circuit breaker |
| Testing | Unit test và integration test đơn giản hơn vì hệ thống tập trung | Test phức tạp hơn do nhiều service, nhiều dependency, nhiều luồng giao tiếp |
| Logging/Monitoring | Theo dõi một ứng dụng/process tương đối đơn giản | Cần centralized logging, distributed tracing, metrics cho từng service |
| Tổ chức team | Nhiều team cùng sửa một codebase, dễ conflict | Mỗi team có thể sở hữu một hoặc vài service riêng |
| Phù hợp khi | Hệ thống nhỏ, team nhỏ, MVP, nghiệp vụ chưa ổn định | Hệ thống lớn, nhiều team, cần scale và release độc lập |

Có thể hiểu ngắn gọn: **Monolithic tối ưu cho sự đơn giản ban đầu**

, còn **Microservices tối ưu cho khả năng mở rộng, triển khai độc lập và tổ chức nhiều team**

. Tuy nhiên, Microservices không phải lúc nào cũng tốt hơn Monolithic. Nếu hệ thống còn nhỏ, nghiệp vụ chưa rõ ràng hoặc team chưa có đủ năng lực vận hành DevOps, việc tách microservices quá sớm có thể làm hệ thống phức tạp hơn mức cần thiết.

Một điểm quan trọng trong thiết kế Microservices là không nên tách service chỉ dựa trên bảng trong database hoặc layer kỹ thuật. Ví dụ, không nên tách thành Controller Service

, Repository Service

, Database Service

. Cách tách đúng hơn là dựa trên nghiệp vụ, ví dụ User Service

, Order Service

, Payment Service

, Notification Service

. Cách này giúp mỗi service có trách nhiệm rõ ràng, dữ liệu riêng và có thể được một team sở hữu độc lập.

### 1.2.8 Việc áp dụng Microservices tại các công ty công nghệ lớn

Microservices không xuất hiện ngay từ đầu ở các công ty lớn. Phần lớn các Big Tech ban đầu đều phát triển từ Monolithic hoặc Service-Oriented Architecture đơn giản hơn, sau đó mới dần chuyển sang Microservices khi hệ thống, lượng người dùng và số lượng đội phát triển tăng lên. Điều này cho thấy Microservices thường là kết quả của nhu cầu mở rộng thực tế, chứ không phải lựa chọn bắt buộc cho mọi dự án ngay từ đầu.

## 1.3 Domain Driven Design (DDD)

Domain Driven Design (Thiết kế hướng miền) là một phương pháp tiếp cận phát triển phần mềm phức tạp, được Eric Evans đề xuất trong cuốn sách nổi tiếng "Domain Driven Design: Tackling Complexity in the Heart of Software" (2003). DDD đặt domain (miền nghiệp vụ) làm trung tâm của toàn bộ quá trình thiết kế phần mềm.

### 1.3.1 Mục Tiêu

**Thu hẹp khoảng cách giao tiếp **

giữa domain experts (chuyên gia nghiệp vụ) và developers bằng cách dùng chung một ngôn ngữ (Ubiquitous Language)

**Phản ánh chính xác **

sự phức tạp của nghiệp vụ trong code, không che giấu hay đơn giản hóa domain model

**Tạo ra mô hình phần mềm **

có thể phát triển cùng với sự thay đổi của nghiệp vụ mà không tạo ra technical debt

**Tách biệt các phần **

của hệ thống có ý nghĩa khác nhau bằng Bounded Context

### 1.3.2 Các Khái Niệm Cốt Lõi

| **Khái niệm** | **Định nghĩa và ví dụ** |
| --- | --- |
| Domain | Lĩnh vực nghiệp vụ mà phần mềm giải quyết. Ví dụ: E-commerce domain, Healthcare domain, Banking domain |
| Subdomain | Một phần của domain lớn hơn, tương đối độc lập. E-commerce có: Order Management, Inventory, Payment, Shipping, Customer subdomain |
| Ubiquitous Language | Ngôn ngữ chung được dùng xuyên suốt từ requirement, design đến code. Ví dụ: Dùng "Order" thay vì "Transaction", "Customer" thay vì "User" trong ngữ cảnh đặt hàng |
| Bounded Context | Ranh giới rõ ràng trong đó một domain model cụ thể được định nghĩa và có giá trị. Trong BC này, "Customer" có thuộc tính khác với "Customer" trong BC khác |
| Entity | Đối tượng có identity riêng biệt, tồn tại theo thời gian. Ví dụ: Order (có OrderId), Customer (có CustomerId) |
| Value Object | Đối tượng không có identity, được định nghĩa bởi thuộc tính. Ví dụ: Money (100 USD = 100 USD bất kể instance nào), Address |
| Aggregate | Nhóm entities và value objects được xử lý như một đơn vị nhất quán. Có một Aggregate Root là điểm vào duy nhất. Ví dụ: Order aggregate gồm Order, OrderItems, ShippingAddress |
| Repository | Interface trừu tượng hóa việc lưu trữ và truy xuất aggregates. Code domain không biết đến SQL hay database cụ thể |
| Domain Event | Sự kiện quan trọng xảy ra trong domain. Ví dụ: OrderPlaced, PaymentConfirmed, ItemShipped. Được dùng để giao tiếp giữa các Bounded Context |
| Domain Service | Logic nghiệp vụ không thuộc về entity hay value object cụ thể nào. Ví dụ: PricingService, ShippingCostCalculator |

### 1.3.3 Context Map

Context Map là một công cụ trong DDD dùng để biểu diễn mối quan hệ và tích hợp giữa các Bounded Context. Nó giúp team hiểu toàn cảnh kiến trúc hệ thống và các điểm tích hợp.

Các loại quan hệ giữa Bounded Contexts:

**Shared Kernel: **

Hai BC chia sẻ một phần domain model. Ví dụ: Order BC và Shipping BC cùng dùng AddressModel. Cần coordinate chặt chẽ khi thay đổi

**Customer/Supplier: **

Một BC (Supplier/Upstream) cung cấp dữ liệu, BC kia (Customer/Downstream) tiêu thụ. Upstream publish contract, downstream phải conform

**Conformist: **

Downstream chấp nhận hoàn toàn model của Upstream, không có quyền thay đổi. Thường xảy ra khi tích hợp third-party service

**Anti-Corruption Layer (ACL): **

Downstream xây dựng layer dịch/translate model của Upstream sang model phù hợp với domain của mình. Bảo vệ domain model khỏi bị ảnh hưởng từ ngoài

**Open Host Service: **

Upstream publish một protocol chuẩn, mở (REST API, gRPC) để nhiều Downstream cùng tích hợp

**Published Language: **

Sử dụng ngôn ngữ/format đã được chuẩn hóa (ví dụ: HL7 trong healthcare, FIX trong trading) làm ngôn ngữ trao đổi giữa các BC

### 1.3.4 DDD Trong Microservices

DDD và Microservices là hai phương pháp bổ sung hoàn hảo cho nhau. Bounded Context trong DDD cung cấp cơ sở lý luận vững chắc để phân rã Microservices:

| Mối quan hệ DDD ↔ Microservices |
| --- |
| 1 Bounded Context ≈ 1 Microservice (quy tắc thực hành phổ biến nhất) |
| Ubiquitous Language → Naming conventions trong API và database schema của service |
| Aggregate Root → API endpoint chính của service (GET/POST /orders/{id}) |
| Domain Events → Events được publish lên Message Queue (Kafka) để giao tiếp giữa services |
| Repository Interface → Service's Data Access Layer, ẩn đi chi tiết database |
| Anti-Corruption Layer → API Gateway / Adapter layer khi tích hợp external systems |
| Context Map → Service Communication Diagram trong kiến trúc Microservices |

Tuy nhiên cần lưu ý: không phải lúc nào cũng ánh xạ 1-1 giữa Bounded Context và Microservice. Đôi khi một BC lớn có thể được tách thành nhiều Microservices nhỏ hơn vì lý do scalability, hoặc nhiều BC nhỏ có thể được gộp vào một service để tránh over-engineering.

## 1.4 Case Study: Hệ Thống Healthcare (Luyện Decomposition)

Để minh họa quá trình áp dụng DDD để phân rã hệ thống Monolithic thành Microservices, chúng ta phân tích một hệ thống quản lý bệnh viện thực tế.

### 1.4.1 Mô Tả Bài Toán

| **Bối cảnh: Hệ thống quản lý bệnh viện đa chuyên khoa** |
| --- |
| Quy mô: 500 giường bệnh, 200 bác sĩ, 50 khoa, 1,000 bệnh nhân/ngày |
| Hiện trạng: Monolithic Java application, 500,000 LOC, 1 database Oracle, deploy mỗi 3 tháng |
| Vấn đề: Hệ thống đặt lịch khám chậm trong giờ cao điểm, ảnh hưởng cả module thanh toán và hồ sơ bệnh án |
| Mục tiêu: Chuyển sang Microservices để scale độc lập, cải thiện reliability và tốc độ release |

Các chức năng chính của hệ thống: Đặt lịch hẹn khám, Quản lý hồ sơ bệnh án (EMR), Kê đơn thuốc, Quản lý toa thuốc, Thanh toán và bảo hiểm, Quản lý nhân sự (bác sĩ, y tá), Quản lý giường bệnh/ICU, Phòng xét nghiệm, Chẩn đoán hình ảnh (X-quang, MRI), Báo cáo thống kê.

### 1.4.2 Bước 1: Xác Định Domain

Áp dụng Event Storming và DDD Strategic Design, xác định các subdomain chính:

| **Subdomain** | **Loại** | **Mức độ ưu tiên** |
| --- | --- | --- |
| **Patient Management** | Core Domain | Cao nhất |
| **Appointment Scheduling** | Core Domain | Cao nhất |
| **Electronic Medical Record (EMR)** | Core Domain | Cao nhất |
| **Billing & Insurance** | Supporting Domain | Cao |
| **Pharmacy Management** | Supporting Domain | Cao |
| **Laboratory Management** | Supporting Domain | Cao |
| **Staff Management** | Generic Domain | Trung bình |
| **Reporting & Analytics** | Generic Domain | Trung bình |
| **Notification Service** | Generic Domain | Thấp (dùng 3rd party) |

Core Domain là những subdomain tạo ra lợi thế cạnh tranh, cần đầu tư phát triển internal. Supporting Domain hỗ trợ core domain, có thể outsource hoặc dùng package. Generic Domain không tạo ra lợi thế cạnh tranh, nên dùng off-the-shelf solutions.

### 1.4.3 Bước 2: Xác Định Bounded Context

Phân tích ngôn ngữ và model trong từng context. Lưu ý cùng một khái niệm "Patient" có nghĩa khác nhau trong các context:

| **Bounded Context** | **Định nghĩa thực thể trong context này** |
| --- | --- |
| Patient Registration BC | Patient = {id, name, dob, address, insurance, contact info} — thông tin cá nhân và hành chính. |
| Appointment BC | Patient = {patientId, upcomingAppointments, preferredDoctor, visitHistory} — thông tin phục vụ xếp lịch và lịch sử khám. |
| EMR BC | Patient = {patientId, diagnoses, medications, allergies, lab results, vital signs} — hồ sơ bệnh án điện tử, thông tin lâm sàng. |
| Billing BC | Patient = {patientId, billingAddress, insurancePolicy, paymentHistory, balance} — thông tin tài chính, bảo hiểm và thanh toán. |
| Pharmacy BC | Patient = {patientId, currentPrescriptions, allergies, medication history} — thông tin phục vụ nghiệp vụ kê đơn và cấp phát thuốc. |
| Laboratory BC | Patient = {patientId} — chỉ sử dụng định danh bệnh nhân để tham chiếu tới các chỉ định xét nghiệm (LabTest) và kết quả xét nghiệm (LabResult). |
| Staff Management BC | Staff = {id, role, schedule} — quản lý thực thể nhân viên y tế/bác sĩ thay vì bệnh nhân. |
| Notification BC | User = {userId} — chỉ quan tâm đến định danh người dùng (có thể là Patient hoặc Staff) và trạng thái (status) để gửi thông báo. |

Nhận xét quan trọng: Cùng một thực thể "Patient" nhưng mỗi Bounded Context chỉ quan tâm đến một tập con thuộc tính phù hợp với nghiệp vụ của mình. Đây là lý do tại sao việc share database là Anti-Pattern trong Microservices — mỗi BC nên có model riêng.

### 1.4.4 Bước 3: Phân Rã Thành Microservices

Từ các Bounded Context đã xác định, phân rã thành Microservices cụ thể:

| **Microservice** | **Trách nhiệm & Database** |
| --- | --- |
| Patient Service | CRUD thông tin bệnh nhân, xác minh identity. DB: PostgreSQL (patient_db) |
| Appointment Service | Đặt lịch, hủy lịch, nhắc nhở, quản lý lịch bác sĩ. DB: PostgreSQL (appointment_db) |
| EMR Service (Medical Record) | Lưu trữ, truy xuất hồ sơ bệnh án, diagnoses, vital signs. DB: MongoDB (emr_db) — dữ liệu phi cấu trúc |
| Prescription Service | Kê đơn, kiểm tra drug interactions, lịch sử đơn thuốc. DB: PostgreSQL (prescription_db) |
| Billing Service | Tính phí, xử lý thanh toán, quản lý bảo hiểm, hóa đơn. DB: PostgreSQL (billing_db) |
| Pharmacy Service | Quản lý tồn kho thuốc, cấp phát thuốc, cảnh báo hết thuốc. DB: PostgreSQL (pharmacy_db) |
| Lab Service | Yêu cầu xét nghiệm, lưu kết quả, cảnh báo kết quả bất thường. DB: MongoDB (lab_db) |
| Notification Service | Email/SMS reminder, in-app notifications. Dùng SendGrid + Twilio (3rd party) |
| API Gateway | Single entry point, routing, auth, rate limiting, SSL termination. Không có DB riêng |
| Auth Service | Xác thực, phân quyền, JWT token management. DB: Redis (session) + PostgreSQL (user_auth_db) |

### 1.4.5 Bước 4: Xác Định Quan Hệ

Xác định cách các microservices giao tiếp với nhau, phân loại theo kiểu đồng bộ (synchronous) và bất đồng bộ (asynchronous):

Giao tiếp Synchronous (REST/gRPC) — dùng khi cần kết quả ngay lập tức:

- Client → API Gateway → Auth Service: Xác thực JWT token

- API Gateway → Patient Service: Lấy thông tin bệnh nhân

- Appointment Service → Patient Service: Verify patient exists trước khi tạo appointment

- Appointment Service → Auth Service: Verify doctor's availability

Giao tiếp Asynchronous (Kafka Events) — dùng cho workflows không cần kết quả ngay:

- Appointment Service phát event AppointmentCreated → Notification Service gửi reminder

- EMR Service phát event DiagnosisUpdated → Prescription Service, Lab Service nhận để cập nhật

- Billing Service phát event PaymentCompleted → EMR Service cập nhật trạng thái thanh toán

- Prescription Service phát event PrescriptionIssued → Pharmacy Service cập nhật tồn kho

Nguyên tắc chọn kiểu giao tiếp: Nếu người dùng đang chờ kết quả → synchronous. Nếu là hành động kéo theo (side effect) → asynchronous event.

| 1. Monolithic Architecture: Điểm khởi đầu tốt cho dự án nhỏ, nhưng tạo ra bottleneck khi scale. Hiểu rõ điểm mạnh/yếu để chọn đúng thời điểm chuyển đổi. |
| 2. Microservices Architecture: Giải pháp cho bài toán scale và organizational agility. Đổi lấy operational complexity để có được flexibility và resilience. |
| 3. Domain Driven Design: Công cụ tư duy giúp xác định ranh giới hệ thống đúng đắn. Bounded Context là bridge nối giữa business domain và technical architecture. |
| 4. Case Study Healthcare: Minh họa quy trình 4 bước thực tế: Xác định Domain → Bounded Context → Microservices → Communication Patterns. |

Điều quan trọng nhất cần ghi nhớ: Microservices không phải là silver bullet. Chúng giải quyết vấn đề về organizational scalability và technical scalability, nhưng đổi lại là sự gia tăng đáng kể về độ phức tạp vận hành. DDD cung cấp framework để phân rã hệ thống một cách có nguyên tắc, đảm bảo các ranh giới service phản ánh đúng thực tế nghiệp vụ, không phải chỉ là quyết định kỹ thuật tùy ý.

## 2.3 Thiết kế Product Service

**Bước 1: Xác định lớp**

Các thực thể bên trong Product Context được xác định không chỉ bao gồm thông tin hàng hóa mà còn bọc gói các domain phụ trợ liên quan trực tiếp đến vòng đời hiển thị và phân loại biến thể của sản phẩm.

**Lớp trung tâm (Aggregate Root):**

Product

. Đây là điểm nghẽn truy xuất; mọi thao tác cập nhật thông tin hàng hóa cốt lõi đều phải đi qua lớp này.

**Lớp danh mục:**

Category

. Quản lý phân loại sản phẩm.

**Lớp kế thừa (Đặc thù ngành hàng):**

Book

, Clothes

, Shoe

, Laptop

, Tablet

, Phone

, Camera

, Watch

, Furniture

. Thiết kế này giải quyết sự khác biệt về cấu trúc dữ liệu của từng loại sản phẩm cụ thể.

**Hệ thống lớp Biến thể và Thuộc tính (Variant & Attributes):**

Thay vì lưu thuộc tính động dạng JSON, thiết kế mới sử dụng mô hình quan hệ chặt chẽ để quản lý biến thể:

Product_Variant

: Quản lý các phiên bản cụ thể của một sản phẩm (có giá và tồn kho riêng).

Attribute

và AttributeValue

: Quản lý danh mục thuộc tính (ví dụ: Màu sắc, Kích thước) và các giá trị của chúng (ví dụ: Đỏ, XL).

Product_Variant_Options

: Lớp trung gian ánh xạ giữa một biến thể cụ thể và các giá trị thuộc tính của nó.

**Bước 2: Xác định thuộc tính (Attributes)**

Cấu trúc thuộc tính được chuẩn hóa theo mô hình quan hệ. Khóa chính (Id) của tất cả các bảng được thiết kế dưới dạng chuỗi (varchar).

**Lớp Product**

- Id: varchar (Primary Key)

- CategoryId: varchar (Foreign Key)

- Name: varchar

- Base_price: float

- Image_url: varchar

- Created_at: date

- Updated_at: date

- Description: varchar

**Lớp Category**

- Id: varchar

- Name: varchar

- Description: varchar

**Các Lớp Kế thừa từ Product (Lưu trữ thông số kỹ thuật đặc thù)**

**Book:**

Author (varchar), Isbn (varchar), Publisher (varchar), ProductId (FK)

**Clothes:**

Brand (varchar), Material (varchar), ProductId (FK)

**Shoe:**

Shoe_type (varchar), Material (varchar), ProductId (FK)

**Laptop:**

Cpu (varchar), Ram (varchar), Storage (varchar), ProductId (FK)

**Tablet:**

Screen_size (varchar), Os (varchar), ProductId (FK)

**Phone:**

Screen_size (varchar), Battery (integer), ProductId (FK)

**Camera:**

Brand (varchar), Sensor_type (varchar), ProductId (FK)

**Watch:**

Brand (varchar), Style (varchar), ProductId (FK)

**Furniture:**

Material (varchar), Dimensions (varchar), ProductId (FK)

**Hệ thống Quản lý Biến thể (Variants)**

**Lớp Product_Variant**

- Id: varchar

- ProductId: varchar (FK trỏ về Product gốc)

- Sku: varchar (Mã định danh kho cho từng biến thể)

- Price: float (Giá riêng của biến thể)

- Stock_quantity: integer (Số lượng tồn kho)

- Image_url: varchar

**Lớp Attribute (Định nghĩa thuộc tính)**

- Id: varchar

- Name: varchar (VD: "Màu sắc", "Dung lượng")

**Lớp AttributeValue (Giá trị của thuộc tính)**

- Id: varchar

- AttributeId: varchar (FK trỏ về Attribute)

- Value: varchar (VD: "Đỏ", "256GB")

**Lớp Product_Variant_Options (Bảng trung gian)**

- Id: varchar

- Product_VariantId: varchar (FK)

- AttributeValueId: varchar (FK)

**Bước 3: Xác định quan hệ**

**Association: Product - Category**

Ký hiệu: *

- 1

(Nhiều Product thuộc về 1 Category).

- Giải thích: Một danh mục (Category) chứa nhiều sản phẩm (Product), mỗi sản phẩm được gắn trực tiếp với một danh mục thông qua trường CategoryId.

**Inheritance (Generalization): Các lớp đặc thù ngành hàng (Book, Laptop, Phone...) - Product**

Giải thích: Đây là quan hệ "is-a" (a-kind-of). Dưới góc độ hạ tầng CSDL quan hệ (RDBMS), mô hình kế thừa này được hiện thực hóa bằng kỹ thuật phân mảnh (table-per-type). Mỗi bảng con có khóa ngoại ProductId

liên kết 1-1 về bảng Product

gốc.

**Composition: Product - Product_Variant**

Ký hiệu: 1

- 1..*

(Hình thoi đặc bên phía Product).

- Giải thích: Quan hệ "has-parts" vòng đời phụ thuộc vật lý. Một variant không thể tồn tại độc lập nếu Product gốc bị xóa.

**Association & Many-to-Many: Variant - Attribute Mapping**

Giải thích: Một Attribute

(Thuộc tính) có nhiều AttributeValue

(Giá trị) (quan hệ 1-N).

Một Product_Variant

được cấu thành từ nhiều AttributeValue

(ví dụ: Biến thể Áo thun vừa có Màu Đỏ, vừa có Size L), và một AttributeValue

có thể thuộc về nhiều Biến thể. Quan hệ N-N này được giải quyết thông qua bảng trung gian Product_Variant_Options

. Cấu trúc này giúp hệ thống linh hoạt mở rộng các loại thuộc tính mà không cần thay đổi schema cơ sở dữ liệu (tương tự mô hình EAV).

## 2.4 Thiết kế User Service

**Bước 1: Xác định lớp**

Các thực thể bên trong User Context chịu trách nhiệm quản lý thông tin định danh, hồ sơ cá nhân và hệ thống phân quyền (RBAC - Role-Based Access Control) của hệ thống.

**Lớp trung tâm (Aggregate Root):**

User

. Đây là thực thể cốt lõi quản lý thông tin đăng nhập và trạng thái tài khoản.

**Lớp kế thừa (Phân loại người dùng):**

Admin

, Staff

, Customer

. Thiết kế này cho phép tách biệt các thông tin nghiệp vụ đặc thù của từng nhóm người dùng mà không làm phình to bảng User gốc.

**Lớp phụ thuộc (Thành phần mở rộng):**

Address

. Quản lý thông tin địa chỉ liên hệ/giao hàng. Việc tách riêng giúp một người dùng có thể linh hoạt sở hữu nhiều địa chỉ khác nhau.

**Hệ thống Phân quyền:**

Role

và Permission

. Quản lý vai trò và quyền hạn chi tiết của từng tài khoản, giúp kiểm soát quyền truy cập vào các tài nguyên của hệ thống.

**Bước 2: Xác định thuộc tính (Attributes)**

Cấu trúc cơ sở dữ liệu được chuẩn hóa, sử dụng kiểu chuỗi (varchar) cho các khóa chính (Id) và khóa ngoại.

**Lớp User (Bảng gốc)**

- Id: varchar (Primary Key)

- Username: varchar

- Password: varchar

- Email: varchar

- Is_activate: bit (Lưu trạng thái kích hoạt tài khoản dạng boolean)

- Full_name: varchar

**Các Lớp Kế thừa từ User (Lưu thông tin đặc thù)**

**Admin:**

UserId (FK - trỏ về User), Rank (varchar)

**Staff:**

UserId (FK - trỏ về User), Employee_id (varchar), Rank (varchar)

**Customer:**

UserId (FK - trỏ về User), Loyalty_points (float - Điểm thành viên)

**Lớp Address**

- Id: varchar

- UserId: varchar (FK trỏ về User)

- Street: varchar

- City: varchar

**Hệ thống Phân quyền (RBAC)**

**Lớp Role (Vai trò):**

- Id: varchar

- UserId: varchar (FK trỏ về User - Ánh xạ vai trò trực tiếp cho người dùng)

- Name: varchar

**Lớp Permission (Quyền hạn):**

- Id: varchar

- Name: varchar

- Description: varchar

**Lớp Role_Permission (Bảng trung gian):**

- Id: varchar

- RoleId: varchar (FK)

- PermissionId: varchar (FK)

**Bước 3: Xác định quan hệ**

**Inheritance (Generalization): Admin, Staff, Customer → User**

Giải thích: Đây là quan hệ "is-a". Tương tự như Product, hệ thống RDBMS hiện thực hóa bằng mô hình phân mảnh (table-per-type). Các bảng con (Admin

, Staff

, Customer

) không có khóa chính độc lập mà sử dụng UserId

làm khóa ngoại (đồng thời đóng vai trò khóa chính) để liên kết 1-1 với bảng User

gốc.

**Composition/Aggregation: User → Address**

Ký hiệu: 1

- 0..*

Giải thích: Một tài khoản User

có thể có không hoặc nhiều địa chỉ (Address

). Vòng đời của Address phụ thuộc vào User (nếu User bị xóa, các địa chỉ liên quan cũng không còn ý nghĩa).

**Association: User → Role**

Giải thích: Dựa trên thiết kế ERD, bảng Role

giữ khóa ngoại UserId

, thể hiện quan hệ 1-N (Một User

có thể được gán một hoặc nhiều Role

cụ thể).

**Many-to-Many: Role ↔ Permission**

Giải thích: Một vai trò (Role

) bao gồm nhiều quyền hạn (Permission

), và một quyền hạn có thể được cấp cho nhiều vai trò khác nhau. Quan hệ N-N này được tách ra thành hai quan hệ 1-N thông qua bảng trung gian Role_Permission

, đảm bảo tính chuẩn hóa dữ liệu và dễ dàng mở rộng quyền hạn sau này.

## 2.5 Thiết kế Cart Service

**Bước 1: Xác định lớp**

Các thực thể trong Cart Context được thiết kế tối giản để tối ưu hóa tốc độ xử lý các thao tác thêm/sửa/xóa vật phẩm trong giỏ hàng trước khi tiến hành thanh toán.

**Lớp trung tâm (Aggregate Root):**

Cart

. Đây là thực thể quản lý giỏ hàng tổng thể của một người dùng. Mỗi người dùng thường chỉ sở hữu một giỏ hàng hoạt động tại một thời điểm.

**Lớp thành phần (Component):**

CartItem

. Đại diện cho một dòng sản phẩm cụ thể nằm trong giỏ hàng. Lớp này không tồn tại độc lập mà luôn gắn liền với một thực thể Cart

.

**Bước 2: Xác định thuộc tính (Attributes)**

Hệ thống tiếp tục sử dụng kiểu chuỗi (varchar) cho các trường định danh để đảm bảo tính đồng nhất với các Service khác.

**Lớp Cart**

**Id:**

varchar(255) (Primary Key).

**User_id:**

varchar(255) (Lưu ID của người dùng. Lưu ý: Chỉ lưu ID để giữ tính lỏng lẻo - loose coupling - giữa Cart Service và User Service).

**Lớp CartItem**

**Id:**

varchar(255) (Primary Key).

**CartId:**

varchar(255) (Foreign Key trỏ về Cart).

**Product_id:**

varchar(255) (Lưu ID của sản phẩm hoặc biến thể sản phẩm từ Product Service).

**Quantity:**

integer(10) (Số lượng sản phẩm người dùng muốn mua).

**Bước 3: Xác định quan hệ**

**Composition: Cart → CartItem**

**Ký hiệu:**

1

→ 0..*

(Hình thoi đặc bên phía Cart).

**Giải thích:**

Đây là quan hệ chứa đựng (Composition) chặt chẽ. Một giỏ hàng có thể chứa nhiều vật phẩm. Quan hệ này thể hiện sự phụ thuộc hoàn toàn về vòng đời:

CartItem

không có ý nghĩa nếu không nằm trong một Cart

.

Khi thực thể Cart

bị xóa (ví dụ: sau khi đặt hàng thành công hoặc người dùng xóa giỏ), tất cả các CartItem

liên quan cũng sẽ bị xóa bỏ hoàn toàn khỏi cơ sở dữ liệu để đảm bảo tính toàn vẹn.

**Loose Coupling (Liên kết lỏng lẻo):**

Mối quan hệ giữa Cart

với User

và CartItem

với Product

không được thể hiện bằng quan hệ vật lý (FK cứng trong DB) giữa các Service, mà thông qua việc lưu trữ ID. Điều này cho phép Cart Service hoạt động độc lập, giúp hệ thống dễ dàng mở rộng theo kiến trúc Microservices.

## 2.6 Thiết kế Order Service

**Bước 1: Xác định lớp**

Order Context đóng vai trò là "trung tâm điều phối" các nghiệp vụ sau khi người dùng quyết định mua hàng. Các thực thể được thiết kế để lưu giữ trạng thái cuối cùng của một giao dịch kinh tế.

**Lớp trung tâm (Aggregate Root):**

Order

. Lưu trữ thông tin tổng quát về đơn hàng, trạng thái xử lý và các tham chiếu đến khách hàng/khuyến mãi.

**Lớp thành phần (Component):**

* Order_Item

: Lưu trữ chi tiết các sản phẩm trong đơn hàng. Đây là bản "snapshot" thông tin sản phẩm tại thời điểm mua (giá, số lượng) để tránh bị ảnh hưởng khi dữ liệu sản phẩm gốc thay đổi.

Payment_Transaction

: Lưu trữ lịch sử các giao dịch thanh toán liên quan đến đơn hàng, hỗ trợ theo dõi dòng tiền và các cổng thanh toán ngoại vi.

**Bước 2: Xác định thuộc tính (Attributes)**

**Lớp Order (Bảng đơn hàng)**

**Id:**

varchar(255) (Primary Key).

**Status:**

varchar(255) (Trạng thái đơn hàng: Chờ xác nhận, Đã thanh toán, Đang giao, Hoàn tất...).

**PaymentMethod:**

varchar(255) (Phương thức thanh toán: COD, Chuyển khoản, Ví điện tử...).

**Voucher_id:**

varchar(255) (Tham chiếu đến mã giảm giá đã áp dụng).

**Customer_id:**

varchar(255) (Tham chiếu đến người mua từ User Service).

**Shipping_address_id:**

varchar(255) (Tham chiếu đến địa chỉ giao hàng cụ thể).

**Created_at:**

varchar(255) (Thời điểm tạo đơn hàng).

**Lớp Order_Item (Chi tiết đơn hàng)**

**Id:**

varchar(255) (Primary Key).

**OrderId:**

varchar(255) (Foreign Key trỏ về Order).

**Product_id:**

varchar(255) (Tham chiếu đến sản phẩm/biến thể đã mua).

**Price:**

float(10) (Giá sản phẩm tại thời điểm chốt đơn - cực kỳ quan trọng để hạch toán chính xác).

**Quantity:**

integer(10) (Số lượng mua).

**Lớp Payment_Transaction (Giao dịch thanh toán)**

**Id:**

varchar(255) (Primary Key).

**OrderId:**

varchar(255) (Foreign Key trỏ về Order).

**Payment_id:**

varchar(255) (Mã tham chiếu từ phía đơn vị thanh toán hoặc cổng thanh toán như VNPay, Momo, PayPal).

**Bước 3: Xác định quan hệ**

**Composition: Order → Order_Item**

**Ký hiệu:**

1

→ 1..*

(Hình thoi đặc bên phía Order).

**Giải thích:**

Một đơn hàng bắt buộc phải có ít nhất một vật phẩm. Quan hệ Composition đảm bảo rằng nếu đơn hàng bị hủy hoặc xóa khỏi hệ thống trong các giai đoạn đầu, các dòng chi tiết sản phẩm đi kèm cũng sẽ bị xóa tự động, tránh rác dữ liệu.

**Composition: Order → Payment_Transaction**

**Ký hiệu:**

1

→ 1..*

(Hình thoi đặc bên phía Order).

**Giải thích:**

Thể hiện mối ràng buộc chặt chẽ giữa đơn hàng và các giao dịch tài chính liên quan. Việc cho phép quan hệ 1..*

hỗ trợ các trường hợp đơn hàng thanh toán nhiều lần hoặc các giao dịch bị lỗi và thực hiện lại (retries). Khi đơn hàng bị xóa, lịch sử giao dịch tương ứng cũng được xử lý đồng bộ.

**Loose Coupling qua ID:**

Tương tự các service trước, Order

liên kết với Customer

, Voucher

, Shipping_address

và Product

thông qua ID chuỗi thay vì liên kết trực tiếp cấp CSDL. Điều này cho phép hệ thống duy trì tính toàn vẹn dữ liệu ngay cả khi các Service khác thực hiện bảo trì hoặc thay đổi hạ tầng.

## 2.7 Thiết kế Payment Service

**Bước 1: Xác định lớp**

Payment Context chịu trách nhiệm xử lý các giao dịch tài chính thực tế thông qua các cổng thanh toán bên thứ ba, đảm bảo tính minh bạch và khả năng đối soát cho hệ thống.

**Lớp trung tâm (Aggregate Root):**

Payment

. Thực thể quản lý một yêu cầu thanh toán cụ thể gắn liền với một đơn hàng. Nó giữ vai trò kiểm soát trạng thái dòng tiền của giao dịch.

**Lớp danh mục:**

Payment_Method

. Quản lý danh sách các phương thức thanh toán được hệ thống hỗ trợ (ví dụ: Thẻ tín dụng, Ví điện tử, ATM nội địa).

**Lớp ghi vết (Logging):**

Payment_Log

. Lưu trữ các phản hồi kỹ thuật chi tiết từ phía cổng thanh toán (Gateway). Đây là dữ liệu nền tảng để xử lý các tranh chấp hoặc lỗi phát sinh trong quá trình giao dịch.

**Bước 2: Xác định thuộc tính (Attributes)**

**Lớp Payment (Bảng Thanh toán)**

**Id:**

varchar(255) (Primary Key).

**Payment_MethodId:**

varchar(255) (Foreign Key trỏ về Payment_Method).

**Order_id:**

varchar(255) (Tham chiếu ID của đơn hàng từ Order Service).

**Amount:**

float(10) (Số tiền cần thanh toán của giao dịch này).

**Currency:**

varchar(255) (Loại tiền tệ được sử dụng, ví dụ: "VND", "USD").

**Status:**

varchar(255) (Trạng thái thanh toán: Chờ xử lý, Thành công, Thất bại).

**Created_at:**

varchar(255) (Thời điểm tạo yêu cầu thanh toán).

**Lớp Payment_Method (Phương thức thanh toán)**

**Id:**

varchar(255) (Primary Key).

**Name:**

varchar(255) (Tên phương thức hiển thị cho người dùng).

**Provider:**

varchar(255) (Tên đơn vị cung cấp giải pháp, ví dụ: "VNPay", "Stripe").

**Lớp Payment_Log (Nhật ký thanh toán)**

**Id:**

varchar(255) (Primary Key).

**PaymentId:**

varchar(255) (Foreign Key trỏ về giao dịch Payment gốc).

**Gateway_id:**

varchar(255) (Mã định danh giao dịch duy nhất được trả về từ phía cổng thanh toán).

**Response_code:**

varchar(255) (Mã kết quả trả về từ Gateway để xác định lý do thành công hoặc lỗi).

**Bước 3: Xác định quan hệ**

**Association: Payment_Method → Payment**

**Ký hiệu:**

1

→ 0..*

.

**Giải thích:**

Một phương thức thanh toán có thể được áp dụng cho nhiều bản ghi thanh toán khác nhau. Ngược lại, mỗi yêu cầu thanh toán chỉ được phép liên kết với duy nhất một phương thức tại một thời điểm.

**Composition: Payment → Payment_Log**

**Ký hiệu:**

1

→ 1..*

(Hình thoi đặc bên phía Payment).

**Giải thích:**

Đây là quan hệ chứa đựng (Composition) chặt chẽ. Mỗi giao dịch thanh toán có thể phát sinh nhiều bản ghi log (ví dụ: một log khi gửi yêu cầu và một log khi nhận kết quả callback). Các bản ghi nhật ký này không có ý nghĩa tồn tại độc lập và sẽ bị hủy bỏ hoàn toàn nếu thực thể Payment

tương ứng bị xóa khỏi hệ thống.

**Loose Coupling:**

* Mối quan hệ giữa Payment

và Order

được thực hiện qua Order_id

dạng chuỗi, đảm bảo Service này có thể hoạt động tách biệt, chỉ quan tâm đến kết quả thanh toán của định danh đơn hàng đó mà không cần truy cập trực tiếp vào logic của Order Service.

## 2.8 Thiết kế Shipping Service

Ship_Tracking

và liên kết với người dùng thông qua Contact_id

. Việc không sử dụng khóa ngoại cứng (Physical FK) tới các database của Service khác giúp Shipping Service có thể tích hợp linh hoạt với nhiều đơn vị vận chuyển trung gian hoặc dễ dàng bảo trì độc lập.

**Tính toàn vẹn dữ liệu:**

Dữ liệu Address

trong bảng Shipment

được lưu trực tiếp dưới dạng chuỗi (thay vì chỉ tham chiếu ID) để đảm bảo rằng ngay cả khi người dùng thay đổi địa chỉ trong tương lai, thông tin giao hàng trên vận đơn cũ vẫn được giữ nguyên đúng như tại thời điểm tạo lệnh giao.

Voucher

## 2.11 Luồng hệ thống tổng thể

**Bước 1: Tiếp nhận và Xác thực định danh (User Service)**

Điểm chạm đầu tiên của mọi luồng request từ phía client là API Gateway. Tại chốt chặn này, hệ thống sẽ tiến hành bóc tách token JWT và giao tiếp với User Service để xác thực người dùng theo cơ chế phi trạng thái (stateless). Việc định danh này là bắt buộc và phải hoàn tất trước khi luồng dữ liệu được phép đi sâu vào các dịch vụ nghiệp vụ bên trong mạng lưới.

**Bước 2: Truy xuất danh mục hàng hóa (Product Service)**

Sau khi bước xác thực thành công, đối với các tác vụ mang tính chất đọc dữ liệu (read-heavy) như xem chi tiết hay tìm kiếm sản phẩm, API Gateway sẽ điều hướng trực tiếp luồng truy cập đến Product Service. Nhờ việc thiết kế cơ sở dữ liệu tách biệt và loại bỏ triệt để các lệnh SQL JOIN sang bảng người dùng, dịch vụ này sở hữu khả năng tự động mở rộng (auto-scaling) một cách độc lập. Yếu tố này đóng vai trò then chốt giúp hệ thống trụ vững trước lượng truy cập khổng lồ trong các kỳ Flash Sale mà không gây ra hiện tượng thắt cổ chai ở tầng cơ sở dữ liệu.

**Bước 3: Thao tác Giỏ hàng (Cart Service)**

Khi khách hàng phát sinh hành động chọn mua sản phẩm, hệ thống sẽ đẩy lệnh ghi (write) xuống Cart Service. Nhận thấy đặc thù của giỏ hàng là tần suất I/O (đọc/ghi) cực kỳ cao nhưng vòng đời dữ liệu lại rất ngắn, kiến trúc này chỉ lưu lại các khóa định danh cơ bản (bao gồm user_id

và product_id

) trên bộ nhớ tạm. Quyết định cắt đứt hoàn toàn khóa ngoại vật lý với Product Service giúp luồng mua sắm của người dùng được duy trì liền mạch, ngay cả trong trường hợp dịch vụ sản phẩm gặp sự cố ngắt kết nối tạm thời.

**Bước 4: Khởi tạo và Điều phối Đơn hàng (Order Service)**

Quá trình chốt đơn (checkout) là điểm hội tụ độ phức tạp kiến trúc lớn nhất của hệ thống. Khi request dạng POST chạm tới Order Service, dịch vụ này sẽ đứng ra làm vai trò trung tâm điều phối (Orchestrator). Nó thực hiện các lệnh gọi đồng bộ (thông qua REST hoặc gRPC) đến Cart Service để chốt danh sách mặt hàng và Product Service để lấy mức giá cuối cùng.

Tại khoảnh khắc này, hệ thống chủ động phá vỡ ranh giới ACID toàn cục. Thay vì dùng giao thức 2PC (Two-Phase Commit) vốn dễ gây lỗi khóa chết (deadlock), hệ thống triển khai mẫu thiết kế Saga. Order Service chỉ lưu bản ghi đơn hàng ở trạng thái PENDING

tại database cục bộ, rồi lập tức trả về mã HTTP 200 cho client để giải phóng luồng. Mọi tác vụ xử lý tốn tài nguyên phía sau đều được đẩy vào các tiến trình chạy ngầm (background).

**Bước 5: Xử lý Giao dịch Tài chính (Payment Service)**

Kể từ bước này, luồng thực thi chuyển hẳn sang cơ chế giao tiếp bất đồng bộ (Event-Driven). Order Service sẽ phát lệnh yêu cầu thanh toán sang Payment Service. Dịch vụ thanh toán sẽ trực tiếp làm việc với các cổng thanh toán bên thứ 3 và tự đóng gói, cô lập mọi lỗi timeout trong không gian của riêng nó để không làm treo hệ thống lõi. Sau khi xác nhận tiền đã được trừ thành công, Payment Service đóng vai trò là một nhà xuất bản (Publisher), phát đi một sự kiện (ví dụ: PaymentCompletedEvent

) lên hệ thống Message Broker thay vì gọi API để cập nhật dữ liệu chéo.

**Bước 6: Kích hoạt Vận chuyển và Hoàn tất (Shipping Service)**

Sự kiện thanh toán thành công được đẩy lên Message Broker sẽ ngay lập tức kích hoạt hai luồng xử lý song song ở các dịch vụ đang đăng ký theo dõi (Subscriber):

Thứ nhất, **Order Service**

bắt được sự kiện và tự động cập nhật trạng thái đơn hàng từ PENDING

sang APPROVED

.

Thứ hai, **Shipping Service**

đồng thời tiêu thụ sự kiện này để sinh ra bản ghi vận đơn (Shipment), tách bạch hoàn toàn logic vận hành kho bãi và điều phối giao nhận ra khỏi vòng đời của một hóa đơn tài chính.

Nhìn chung, kiến trúc phân luồng này thể hiện rõ chiến lược thiết kế: sử dụng mặt ngoài đồng bộ để đảm bảo tốc độ phản hồi tức thì cho client, và sử dụng mặt trong bất đồng bộ để duy trì hệ sinh thái liên kết lỏng lẻo. Đây là sự đánh đổi chủ đích—từ bỏ tính nhất quán dữ liệu ngay thời điểm thực để tối ưu hóa khả năng cô lập lỗi và tính khả dụng của toàn hệ thống.

## 2.12 Kết luận

Việc tái cấu trúc một nền tảng E-commerce nguyên khối thành các Microservices độc lập không phải là viên đạn bạc giải quyết mọi vấn đề, mà thực chất là một sự đánh đổi có chủ đích về mặt hạ tầng. Chúng ta chấp nhận đối mặt với độ trễ của mạng lưới và độ phức tạp của bài toán đồng bộ dữ liệu phân tán, để đổi lấy khả năng mở rộng linh hoạt tại các "điểm nghẽn" và tối ưu hóa tính sẵn sàng của toàn hệ thống.

Trong quá trình thiết kế, phương pháp Domain-Driven Design (DDD) đóng vai trò là kim chỉ nam nền tảng. Nếu không vạch ra các ranh giới ngữ cảnh (Bounded Context) một cách nghiêm ngặt, kiến trúc sẽ rất dễ thoái hóa thành một "khối nguyên khối phân tán" (distributed monolith) đầy rủi ro. Bằng cách phân mảnh cơ sở dữ liệu, cấm tuyệt đối việc sử dụng SQL JOIN xuyên mạng và chỉ cho phép giao tiếp thông qua các hợp đồng API (API contracts), mỗi service đã duy trì được mức độ tự trị cao nhất. Cơ chế này ngăn chặn triệt để tình trạng khóa bảng chéo, giữ cho luồng giao dịch cốt lõi luôn an toàn trước nguy cơ sụp đổ dây chuyền.

Về mặt công nghệ cài đặt, framework Django và Django REST Framework (DRF) mang lại tốc độ phát triển API vô cùng nhanh chóng. Dù bản chất ban đầu của Django được tối ưu cho mô hình Monolithic, nhưng khi kết hợp với quy hoạch mã nguồn theo hướng domain, nó hoàn toàn có thể bọc gói các RESTful API hiệu quả. Tuy vậy, các kỹ sư phần mềm phải chủ động can thiệp để vô hiệu hóa các ràng buộc khóa ngoại (Foreign Key) mặc định của Django ORM giữa các ứng dụng, nhằm bảo vệ sự cô lập dữ liệu tuyệt đối cho từng tiến trình.

Cuối cùng, một hệ thống E-commerce với các chức năng quản lý nghiệp vụ cơ bản (CRUD) mới chỉ là lớp nền tảng. Giá trị cốt lõi và lợi thế cạnh tranh thực sự nằm ở khối lượng dữ liệu hành vi (behavior data) khổng lồ được thu thập từ mạng lưới microservices này. Trong chương tiếp theo, trọng tâm nghiên cứu sẽ được chuyển sang phân hệ AI Service, nhằm giải quyết bài toán biến nguồn dữ liệu thô này thành các hệ thống Gợi ý cá nhân hóa (Recommendation System) và Chatbot hỗ trợ thông minh, qua đó trực tiếp thúc đẩy tỷ lệ chuyển đổi đơn hàng cho nền tảng.

## 3.4 Mô hình Sequence Modeling (LSTM/BiLSTM + Attention)

### 3.4.1 Tiền xử lý và Xây dựng chuỗi dữ liệu

**Tính khả thi thực tế (Top-5 Accuracy):**

Ma trận xuất hiện một vệt sáng dọc nổi bật tại index 8 (Lớp sản phẩm số 9). Báo cáo Classification Report chỉ ra lớp này có Recall cực cao (0.70) nhưng Precision chạm đáy (0.26). ## 4.2 Kiến trúc hệ thống

**4.2.1. Tổng quan**

Hệ thống ecom-final (TruongShop AI-Ecom) là một nền tảng thương mại điện tử phân tán hoàn toàn. Kiến trúc này tuân thủ các nguyên tắc thiết kế doanh nghiệp hiện đại, đảm bảo tính mở rộng (scalability), dễ bảo trì (maintainability) và cô lập lỗi (fault isolation). Mỗi miền nghiệp vụ cốt lõi là một microservice Django độc lập, kết hợp cùng sức mạnh từ các AI service viết bằng FastAPI.

**4.2.2. Kiến trúc Microservice (Microservice Architecture)**

Hệ thống bao gồm các miền dịch vụ chính:

**User/Auth Service:**

Xử lý xác thực JWT, phân quyền và quản lý tài khoản.

**Product Service:**

**Order & Payment Service:**

Quản lý vòng đời đơn hàng, giao dịch thanh toán.

**Tracking Service:**

Ghi nhận hành vi người dùng (view, click, cart, purchase).

**AI Services (Recommendation, Chatbot):**

Phân tích ngữ cảnh, vector search và tư vấn khách hàng tự động.

**4.2.3. API Gateway**

Lớp API Gateway được giới thiệu như một điểm tiếp nhận duy nhất cho mọi request từ client. Trái với kiến trúc dùng Nginx mặc định, dự án này triển khai Gateway bằng Django. Nó đảm nhiệm:

Routing (định tuyến) các request /api/*

tới đúng microservice nội bộ.

- Render các trang Web UI (trang chủ, giỏ hàng, profile).

- Thực thi các chính sách chung như timeout và retry cơ bản.

**4.2.4. Giao tiếp giữa các Service (Service Communication)**

Hệ thống áp dụng chiến lược giao tiếp lai (Hybrid):

**Giao tiếp đồng bộ (Synchronous):**

Sử dụng HTTP RESTful API cho các thao tác yêu cầu kết quả ngay (VD: Gateway gọi Product Service để lấy thông tin sản phẩm).

**Giao tiếp bất đồng bộ (Asynchronous):**

Sử dụng Message Broker (RabbitMQ) kết hợp Outbox Pattern cho luồng hướng sự kiện. Ví dụ: Khi Auth Service tạo user mới, một event sẽ được đẩy vào RabbitMQ để customer-service

nhận và đồng bộ hồ sơ.
